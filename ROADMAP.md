## Vision

**The actual goal (clarified 2026-08-19): get models into production and build a shared feature store.** Not, right now, to make money betting — there's no confidence yet that this has a real edge or the leverage to act on one. The bar for what ships is "not trash" (real, defensible signal), not "beats the market." That means the economic/CLV layer (§ below) is explicitly low-priority — it matters before any real staking, not before production.

An end-to-end MLB ML system for DraftKings prop research: a shared feature store feeding **multiple models** (batter hit/no-hit, pitcher K/no-K, others as they prove out).

**Current reality:** one model (`hit_predictor`), one bespoke feature pipeline (not yet on the shared store). Feature-store convergence is deliberately deferred until model #2 exists (see Mid-term).

## Current state (2026-08-22)

- `hit_predictor` v1–v4 are all statistically flat vs. the naive baseline **at the per-PA grain** (log_loss within ~0.001, ROC-AUC 0.51–0.52).
- **Per-game aggregation check: done 2026-08-19, corrected 2026-08-22.** Same model/features aggregated to player-game grain (the grain a DK prop actually resolves on): resolution ~127x higher than PA grain, ROC-AUC 0.516→0.636 — that framing insight still holds. **But the original "model beats naive Brier at game grain" claim was wrong** — it compared the model against the wrong naive floor (Brier's `uncertainty` term, not an actual naive model aggregated the same way the real model is). Corrected via a proper head-to-head (`utils/eval.py::run_pa_vs_game_grain_check`, run through v4): **a properly-aggregated naive baseline beats the model on every game-grain metric** (ROC-AUC 0.6448 vs 0.6361, Brier 0.2230 vs 0.2259). Full writeup: `BENCHMARKS.md` §4.5. **Game grain is still the primary evaluation target**, but "beat naive" is not yet a demonstrated result — see near-term backlog item 1 below (new).
- Root cause of the naive baseline's game-grain edge: it's constant per PA, but a batter's `n_pa` (plate appearances) varies by game, and `1-∏(1-p)` with more PAs mechanically raises P(1+ hit) — real signal the naive model picks up for free that the model isn't clearly beating.
- Separately, aggregated probabilities are currently overconfident (the `1-∏(1-p)` independence assumption doesn't account for correlation across a batter's same-game PAs) — needs recalibration, but note recalibration fixes calibration, not the discrimination gap above. See near-term backlog.
- **v4 (inning-based pitcher-role gating + game context): run 2026-08-22.** Result: statistically flat vs. v2 at both grains (PA ROC-AUC 0.516 vs 0.517, game ROC-AUC 0.636 vs 0.636) — the new features made no measurable difference. `expected_pitcher_role` (inning-based) agreed with the realized role 88.9% of PAs, but v4 changed the role-gating logic and added game-context features in the same experiment, so which change (if either) mattered isn't separable from this run.
- **v5 (4 Tier 1 features: arsenal entropy, pitch-tunneling proxies, extended log5 matchup, velocity-decline trend): run 2026-08-22.** Result: statistically flat vs. v4 at both grains (game ROC-AUC 0.6367 vs v4's 0.6361, Brier 0.2260 vs 0.2259) — naive baseline still wins on every game-grain metric by essentially the same margin as v4. Full numbers in `BENCHMARKS.md` §1. This is meaningful evidence (not proof) that per-PA rate-based feature engineering isn't going to close the naive-baseline gap — none of these 4 features touch `n_pa`, the mechanical driver identified in backlog item 1 below.
- **n_pa pre-game prediction model: v1 baseline built and run 2026-08-22** (`src/models/n_pa_predictor/`, outside this repo's `experiments/v{N}_*` pattern — see `n_pa_predictor/baseline_results.md`). Features: batting_order, home/away, opposing starter's `expected_start_innings` (reused from `hit_predictor.game_context`), batter's own rolling `avg_n_pa_per_game`, batting team's rolling win_pct/runs_scored. **Result: negative.** On val season 2024 (43,039 starter batter-games — parity-verified against `hit_predictor`'s own `create_pa_outcome` starter set, see below), the global-mean naive (MAE 0.4955) beats the batter's-own-rolling-average naive (0.5611), linear regression (0.5420), AND XGBoost (0.5575) — nothing in this v1 feature set demonstrates signal beyond predicting the constant mean. **The n_pa distribution explains why**: 56.8% of starter-games are exactly 4 PA, 94.7% fall in {3,4,5} (mean 4.01, std 0.78) — a constant prediction is already close almost always, and the ~5% tail (1–2 or 6–7 PA) is exactly where early pulls/blowouts/extra-innings live, which no pre-game feature captures. The feature set needs different signal (team implied run total via odds data was explicitly deferred, not yet tried) or this lever may just be intrinsically low-ceiling. **This is evidence against, not for, the hypothesis that predicting `n_pa` closes backlog item 1's naive-baseline gap** — do not wire an unproven `expected_n_pa` into hit_predictor's game-grain aggregation yet.
- **Low-PA-tail investigation: 2026-08-23.** Pulled real 2024 data to test whether n_pa ≤ 3 (early-exit side of the tail) is more predictable, per the "strong pitcher vs weak batter" hypothesis. Confirmed: controlling for batting_order ≥ 6, the opposing starter's WHIP correlates with team PA count that game at +0.47 (strong), while K-rate correlates at ~0.00 — **the mechanism is traffic allowed (walks+hits), not strikeouts**. Added `opp_starter_whip_season` (this-season rolling, SP-role-only, reused `rolling_stats.build_pitcher_rolling_stats_all_roles`) to the v1 feature set and re-ran the full-dataset regression baseline: **still doesn't beat naive** (XGBoost MAE 0.5539 vs naive 0.4955, barely moved from 0.5575 pre-WHIP). Feature importance confirms XGBoost *is* using WHIP (not ignored), just ranked near-bottom (~0.035, vs batting_order's ~0.50) — the effect is real but concentrated in a narrow slice (order ≥ 6) and shifts probability mass at the margin (3 vs 4 PA), which barely registers in whole-population MAE. **Conclusion: full-dataset regression MAE is the wrong lens for this signal.**
- **v1 experiment: `experiments/v1_low_pa_classifier/train.py`, run 2026-08-23 — POSITIVE result, first for this model.** Reframed as binary classification, `low_pa = (n_pa <= 3)`, on the SAME feature set (no filtering — kept full dataset, let the model learn the batting_order × WHIP interaction itself), evaluated by PR-AUC/ROC-AUC + a precision-recall threshold sweep (user's stated priority: precision, since predictions feed betting decisions where a false positive is the costly error). Val season 2024, base rate 19.8%. **Logistic regression beats both naive floors**: PR-AUC 0.440 vs. best-naive (per-slot historical rate lookup) 0.394, ROC-AUC 0.771 vs. 0.754 — and notably beat XGBoost too (PR-AUC 0.414, ROC-AUC 0.756), suggesting the batting_order/WHIP relationship is close to linear in log-odds rather than needing tree-based interaction discovery. **At a 0.6 confidence threshold: 60.7% precision (LR) on 1,214 val predictions (~2.8% of all starter-games), recall 8.6%** — a real, usable lift over the 19.8% base rate. The per-slot naive floor has a hard structural ceiling (its highest possible predicted probability is the top slot's own historical rate, ~0.59) and can never produce a higher-confidence prediction than that; LR/XGBoost's ability to combine batting_order with WHIP is what unlocks genuinely high-confidence predictions above that ceiling. Full precision/recall table and plots (PR curve, calibration, feature importance) in `plots/v1_low_pa_classifier/`, logged to MLflow under experiment `n_pa_predictor`.
- **Operating threshold locked in: 2026-08-23 — 0.85, XGBoost, not the initial 0.6 LR pick.** Added Wilson 95% CIs to the threshold sweep (now permanent in `train.py`, not a one-off) after spotting an apparent LR-vs-XGBoost precision "crossover" around 0.8 — the CIs there overlap almost completely (LR [45.7%, 69.9%] on n=60 vs XGBoost [52.3%, 64.7%] on n=237), confirming it was small-sample noise, not real. Re-swept at finer 0.05 steps from 0.5-0.9 and found the actual best selective operating point further out: **XGBoost @ 0.85 → 64.7% precision, 95% CI [55.6%, 72.8%], n=116 val predictions (2024)** — tighter CI and higher point estimate than anything at 0.8, and it beats LR's aggregate PR-AUC edge specifically in this selective, low-volume region (LR's own n=24 at 0.85 is too thin to trust: CI [35.1%, 72.1%]). Matches the user's stated use case — "not going to be making many bets, it will be selective anyway" — so precision-at-low-volume, not aggregate PR-AUC, is the right thing to have optimized for. **This is the model's production operating point going forward**: XGBoost classifier, `low_pa = (n_pa <= 3)`, confidence threshold 0.85, expect ~1 qualifying prediction every ~2 days across a season (116/season ballpark). **Next:** de-vig comparison against DK's own PA-adjacent prop lines is still required before treating this as a genuine bettable edge — 64.7% raw precision is not automatically +EV against a book's actual price. Then: build a stronger model (more/better features, larger training sample, possibly multi-season val for a more robust CI at this threshold — a single val season's n=116 is still a fairly thin base for a real go/no-go decision).
- **Bug found + fixed 2026-08-22, while building n_pa_predictor: `PBP.PA_OUTCOMES` (schema.py:119, hit_predictor's canonical PA-outcome set) is missing `'Field Error'` (~1,100 PAs/season — reached base on a fielding error, indisputably a completed PA) and `'Sac Fly Double Play'` (~13/season, same category as `'Sac Fly'` which IS included).** Found by comparing n_pa_predictor's starter-game count against `create_pa_outcome`'s own starter set for the same season (was 43,035 vs 43,039 — 4 starters whose ONLY PA that game was a reach-on-error were silently dropped entirely). n_pa_predictor works around this locally (`n_pa_predictor/processing/schema.py`'s own extended `PA_OUTCOMES`), verified to close the gap exactly (43,039 = 43,039, zero mismatches either direction). **Not fixed in hit_predictor's shared `schema.py` itself** — that's used as the "pitcher PA denominator" throughout `season_stats.py`/`rolling_stats.py` (PA totals, TTO capping, rate denominators), so fixing it would shift a lot of existing feature values and invalidate re-running past experiments' exact numbers without a full re-run; a real fix worth doing, but a deliberate call for whoever owns that next `experiments/v{N}_*` cycle, not made unilaterally here.
- **Statistical shrinkage baseline: built and run 2026-08-22** (`baseline/statistical/run_baseline.py`) — a single empirical-Bayes formula (this-season BA-so-far shrunk toward last-season BA, k=100, falling back to league average for rookies), evaluated through the same `run_pa_vs_game_grain_check` harness as everything else, now with a live `summarize_verdict()` call baked into the script. **Corrected result (was initially misread as "beats naive" from ROC-AUC alone — see `BENCHMARKS.md` §1's correction note): verdict is `calibration_only`, not a win.** Reliability beats naive (0.0015 vs 0.0041 — genuinely more honest), but resolution is *worse* than naive (0.0159 vs 0.0182) even though ROC-AUC moved the "right" direction (0.6489 vs 0.6448) — exactly the trap `BENCHMARKS.md` §2 exists to catch. It does beat v5's resolution (0.0159 vs 0.0138), the best of any ML model tried, but a full verdict vs v5 isn't computable — v4/v5 never logged game-grain reliability. Full numbers: `BENCHMARKS.md` §1. Net: naive's resolution edge at game grain is still unbeaten by anything built so far; the shrinkage baseline's real contribution is showing that reliability and resolution can move in different directions, and that per-batter signal (last-season BA, in-season form) narrows the gap without closing it.
- **Matchup-extremity slice check: built and run 2026-08-22** (`baseline/statistical/matchup_extremity_check.py`) — pooled ~150K 2024 val-season PAs into a 3×3 batter-strength × pitcher-dominance grid (`utils/matchup_slicing.py::slice_by_matchup_extremity`, TDD). Finding cuts both ways: even the most extreme pooled matchup (weak batter vs. dominant pitcher, 17,925 PAs) only has a 0.202 observed hit rate — not near-zero, real baseball randomness dominates even lopsided matchups — and the shrinkage baseline ignores pitcher quality entirely (batter-only) despite the data showing a consistent, real pitcher effect within every batter tier.
- **Adding pitcher signal to the shrinkage baseline: two iterations, run 2026-08-23** (`baseline/statistical/run_matchup_baseline.py`, `shrinkage.py::add_matchup_shrinkage_component` + `add_matchup_shrinkage_component_blended`, 12 new tests, TDD; no regression/fitting anywhere — both are closed-form log5 combinations, same convention as `tier1_feats.build_log5_matchup_features`). **v1 (static pitcher term — last-season hit-rate-allowed, frozen all season): verdict `calibration_only` vs batter-only, flat, resolution actually down slightly (0.0159→0.0155).** Diagnosed via Blake Snell's real 2024 game log (`baseline/statistical/pitcher_case_study.py`, identified mechanically as the season's most dominant qualified starter, turned out to be the actual NL Cy Young winner): his pitcher term is frozen at 0.157 all season, but his real 2024 form was shaky through June — the static discount was wrong exactly when it mattered. **v2 (pitcher's own in-season cascade — cumulative hits-allowed-so-far shrunk toward last-season rate, mirroring the batter side's existing treatment exactly): verdict `real_improvement` both vs batter-only (resolution 0.0162, reliability 0.0012 — beats batter-only on every metric) and vs v1 static.** Diagnosis confirmed by fix: early-season predictions for Snell now sit visibly above the static version (hasn't earned the "dominant" discount yet) and converge to it by season's end as in-season sample accumulates. **Still below naive's resolution (0.0162 vs 0.0182)** — real, measured progress, not a full close. Two batter-side case studies (`batter_case_study.py`) — worst (Mitch Garver, 0.146/418 PA) and best (Bobby Witt Jr., 0.301/692 PA, 2nd in AL MVP voting that year) qualified 2024 batters, identified mechanically — show the same model producing cleanly separated, stable predicted bands for real players within weeks, despite per-game raw noise. Full artifact walkthrough (charts + hand-traceable worked tables): `.lavish/eval-metrics-cleanup.html`.
- **Slice diagnostic — "what is the model good/bad at": built and run 2026-08-23** (`baseline/statistical/slice_diagnostic.py`) — reuses `shared/model_dashboard/`'s existing, tested slicing/contribution/bootstrap tooling (built per `CLAUDE.md`'s Model Layer section for exactly this, never wired to `hit_predictor`'s actual predictions before this) against the pitcher-blended shrinkage model's real 2024 predictions. **Confirms, via bootstrap 95% CI, that `times_through_order=3` (batter's 3rd+ PA vs. the same starter) is a real, statistically distinguishable weak spot** (log_loss 0.5469, CI [0.5403, 0.5536], entirely above the overall 0.5286) — not noise, and consistent with Lichtman's TTOP research already cited in `FEATURE_GLOSSARY.md`/`pipeline.py`. `times_through_order=2` is also a real (smaller) gap; `=1` is not distinguishable from overall. **Bigger finding, ranked #1 by contribution:** `pitcher_role` itself is the single largest split — predictions against starters are measurably worse than against bullpen, both confirmed real via bootstrap, in opposite directions — a concrete new thread, not yet investigated. One expected effect that did **not** show up as a confirmed gap: platoon (same-hand) matchup — CI overlaps the overall at this sample size. Tool is reusable for any future slice or model, not a one-off. Full artifact card: `.lavish/eval-metrics-cleanup.html`.

## Mid-term

- **Model #2 — pitcher K props.** `BENCHMARKS.md` §4.4 flags K-rate as structurally stickier than hit outcomes (DIPS-era "three true outcomes" reasoning) — the natural next model. **Baseline built and run 2026-08-23** (`src/models/k_predictor/`, `baseline/model/run.py` + `baseline_results.md`) — POSITIVE on the first pass, ahead of waiting for hit_predictor's open questions to settle. ## Working conventions

- **Per-task plans stay ephemeral.** Use the `/impl-planning` skill (per `CLAUDE.md`'s TDD Requirement) for one task at a time; delete the plan doc once the work merges, same as this session did for `implementation_plan.md`. This file (`ROADMAP.md`) is for standing priorities and direction, not task-level implementation detail.
- **`BENCHMARKS.md`** is the running experiment log (results table) and the place model-quality reasoning lives — update its table after every run, including v4's. **After every experiment (yours or Claude-built), fill in ECE/Reliability/Resolution alongside LogLoss/Brier/ROC-AUC** — reliability (calibration error, lower better) and resolution (discrimination, higher better) together are the real "did this help" signal, not log_loss alone; both are already computed by `evaluate_hit_predictor()` and logged to MLflow automatically (decided 2026-08-19, see `BENCHMARKS.md` §1).
- **Evaluation metrics were formalized 2026-08-22** (`BENCHMARKS.md` §2, `config.yaml`'s `decision_metrics`/`diagnostic_metrics` fields): reliability + resolution at game grain are the *only* decision metrics — "can the prediction be trusted" + "is there real range in the predictions." Everything else (log_loss, Brier, ROC-AUC, PR-AUC, ECE) is diagnostic. `utils/eval.py::summarize_verdict(baseline_metrics, new_metrics)` codifies the comparison (`real_improvement` / `overconfidence_risk` / `calibration_only` / `no_improvement`) and is wired into `utils/run_comparison.py`'s HTML report banner. New experiments (v6+) should call it rather than eyeballing metric deltas — the frozen v1–v5 `train.py` files were deliberately left untouched (see Parked below).
- **`FEATURE_GLOSSARY.md`** is the feature reference — check before adding a feature or wondering if one exists.
- Update this file's "Current state" and "Near-term backlog" sections whenever a backlog item ships or priorities change — that's what keeps it worth reading cold.
