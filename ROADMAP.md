## Production plan (Feature Store / FTI pipelines)

Added 2026-08-31, scoped out from *Building Machine Learning Systems with a Feature Store* (Jim Dowling, O'Reilly 2026) and Feast's own production docs. This is the cross-model build order for actually getting a finalized model into production — every model baseline built so far (`hit_predictor`, `k_predictor`, `n_pa_predictor`, `bb_predictor`, `short_outing_predictor`) still runs as a one-off `experiments/v{N}_*/train.py` script that re-pulls full-season S3 Parquet and trains ad hoc. None has a production feature pipeline, a working feature store, a model registry, or an inference path. k_predictor is the first candidate to walk through this, since it's the model with the longest `real_improvement` track record — but this plan isn't k_predictor-specific.

**The mental model (the "FTI" architecture):** every ML system decomposes into three independent pipelines connected by a shared data layer. **Feature pipelines** turn raw data into reusable, versioned feature tables (batch or incremental) stored in a **feature store**. **Training pipelines** read features, train a model, and register it in a **model registry**. **Inference pipelines** pull a registered model plus fresh feature data and produce predictions. The reason this decomposition matters here specifically: it forces the feature-computation code that training used to be the *same* code an inference job calls later — the single biggest cause of a model that backtests well but is wrong in production is a feature computed one way for training and a subtly different way at serving time.

**Where this repo actually stands today, mapped to the three pipelines:**
- **Feature pipeline — built for research, not production.** A winning feature set (e.g. k_predictor's v6 lineage) lives in bespoke pandas/DuckDB functions under `processing/features/`, but every experiment script re-reads the *entire* season's Parquet from S3 and rebuilds everything from scratch — there's no single program parameterized by `start_time`/`end_time` that can run in backfill mode (recompute history) or incremental mode (yesterday's slice only), which is what a real production feature pipeline needs.
- **Feature store — scaffolded, never exercised.** `src/features/feature_store.yaml` + `feature.py` define real Feast `Entity`/`FeatureView` objects against S3 + DynamoDB, but only for `hit_predictor`'s four original generic feature families — not for any of the actual winning feature sets built since (k_predictor's rolling K-rate/context/CSW% columns included). No `feast apply` has ever run (no `registry.pb` exists anywhere), and no materialization job has ever executed.
- **Training pipeline — closest to done, missing the registry handoff.** MLflow experiment tracking (`mlruns/`) is real. What's missing: a trained model is never saved as a versioned, loadable artifact (`.json` for XGBoost, not `.pkl` — the untyped-code-execution risk `.pkl` carries) tied to the exact feature-view version it trained against, the way a real model registry requires.
- **Inference pipeline — does not exist.** This is Layer 6 in `CLAUDE.md`'s architecture table, still `[not started]` for every model. Nothing pulls today's probable starters, computes their features through the *same* code path training used, loads a registered model, and writes a prediction somewhere.

**Build order** (dependency order — each step needs the one before it to be real, not just designed):
1. **Factor the frozen winning feature set into one incremental-capable feature pipeline**, parameterized by `start_time`/`end_time` rather than "reload the whole season." Requires a model's feature list to actually be frozen first — this is why k_predictor's own finalization checklist (above) is a prerequisite, not a parallel track.
2. **Register those feature tables as real Feast `FeatureView`s and get one `feast apply` + `materialize_incremental()` call working end-to-end for a single day**, proving the feature-store wiring before building anything on top of it.
3. **Fix `daily_feature_create`'s known bugs and bundle the transform modules into its zip** so materialization can run on a schedule — this repo already has the orchestrator (EventBridge → Step Functions → Lambda), it just isn't wired to call step 1's code yet.
4. **Add a model-registry step to training** — serialize the frozen model (`.json` for XGBoost) tied to a specific feature-view version, stored in S3.
5. **Build the batch inference pipeline** — pull tomorrow's probable starters (or equivalent entities per model), call step 1's *same* feature-computation code, load the step-4 model, predict, write to an inference store in S3.

Not started. Revisit once a model's finalization checklist is actually done — starting with k_predictor's (see "Near-term backlog (k_predictor)" above).

  - **Coverage-check mechanism note, recorded 2026-08-26** (prompted by a walkthrough of the `count_distribution_check` artifact — it wasn't obvious from the numbers alone how the per-start pmf actually gets built). Plain-English version: the model is asked N separate small questions — `P(strikeout)` for each of `expected_batters_faced`'s synthetic at-bats — and `poisson_binomial_pmf` just answers "given these N independent-but-different-probability coin flips, how likely is every possible total?" No simulation, pure combinatorics (build the distribution up one at-bat at a time — DP/convolution, `O(N^2)`, exact). **Two things worth keeping straight when reading or reusing this:** (1) N itself is a fixed point estimate going in, not something the pmf is uncertain about — all of its spread comes from not knowing *which* batters whiff, none of it from not knowing *how many* at-bats there will be (this is exactly the gap Story 0's coverage numbers above tested for, and — so far — didn't find evidence of); (2) the pmf's shape is only as good as the N per-at-bat probabilities feeding it — the Poisson-binomial combination step is bookkeeping, it adds no information of its own beyond what those N pregame LR scores already carry. **Planned reuse:** this nominal-vs-empirical coverage-check pattern is intended to become part of production model-monitoring visualization once k_predictor ships (checking live prediction intervals stay honest over time), not just a one-off validation diagnostic — keep `count_distribution.py` and `run.py`'s coverage-check section (Section 7) in mind before simplifying or deleting either.

## Working conventions

- **Per-task plans stay ephemeral.** Use the `/impl-planning` skill (per `CLAUDE.md`'s TDD Requirement) for one task at a time; delete the plan doc once the work merges, same as this session did for `implementation_plan.md`. This file (`ROADMAP.md`) is for standing priorities and direction, not task-level implementation detail.
- **`BENCHMARKS.md`** is the running experiment log (results table) and the place model-quality reasoning lives — update its table after every run, including v4's. **After every experiment (yours or Claude-built), fill in ECE/Reliability/Resolution alongside LogLoss/Brier/ROC-AUC** — reliability (calibration error, lower better) and resolution (discrimination, higher better) together are the real "did this help" signal, not log_loss alone; both are already computed by `evaluate_hit_predictor()` and logged to MLflow automatically (decided 2026-08-19, see `BENCHMARKS.md` §1).
- **Evaluation metrics were formalized 2026-08-22** (`BENCHMARKS.md` §2, `config.yaml`'s `decision_metrics`/`diagnostic_metrics` fields): reliability + resolution at game grain are the *only* decision metrics — "can the prediction be trusted" + "is there real range in the predictions." Everything else (log_loss, Brier, ROC-AUC, PR-AUC, ECE) is diagnostic. `utils/eval.py::summarize_verdict(baseline_metrics, new_metrics)` codifies the comparison (`real_improvement` / `overconfidence_risk` / `calibration_only` / `no_improvement`) and is wired into `utils/run_comparison.py`'s HTML report banner. New experiments (v6+) should call it rather than eyeballing metric deltas — the frozen v1–v5 `train.py` files were deliberately left untouched (see Parked below).
- **`FEATURE_GLOSSARY.md`** is the feature reference — check before adding a feature or wondering if one exists.
- Update this file's "Current state" and "Near-term backlog" sections whenever a backlog item ships or priorities change — that's what keeps it worth reading cold.
