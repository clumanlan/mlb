Why naive still wins resolution — the mechanism

Naive's predicted probability is a pure function of n_pa (PA count that game) — nothing else. That alone is a huge, near-mechanical driver of "did this batter get ≥1 hit." Sorting purely by it cleanly separates a few large groups. Blending in real but comparatively weak skill signal (shrinkage) smears that clean separation more than it adds.

Decision framework, going forward

Grain: game, not plate-appearance. evaluate_hit_predictor() computes reliability/resolution at both grains for every run, but PA-grain values are near-meaningless on their own — a single PA is close to pure variance (Carleton: batting average needs ~910 PA to stabilize). run_pa_vs_game_grain_check() aggregates PA predictions up to one row per batter-game (P(≥1 hit) via 1-∏(1-p)) before scoring, and summarize_verdict()/compute_verdict_for_report() both default to those game-grain numbers (falling back to PA-grain only if game-grain isn't logged).

Why low base rate isn't the real driver of the noise problem

Raised in review: is 0.223 "low enough" that zeros drown out signal generally? Not quite — Bernoulli variance p(1-p) is maximized at p=0.5 and shrinks toward 0 or 1, so a skewed base rate has less raw per-observation noise, not more.

What actually gets worse as p shrinks: (1) relative precision on a rate estimate scales like sqrt((1-p)/(n·p)) — grows as p→0 for fixed n; (2) calibration buckets get starved of actual positive examples (a 0.03 base-rate bucket has ~7x fewer hits than a 0.22 one at the same n) before you even get to the model-vs-noise question. Both compound with small-n evaluation, they don't replace it.

Flagged as relevant to two future models: home runs (~3% per PA — both effects stack, likely needs a much bigger aggregation window than game grain) and the planned K-props model (~22–25% per PA, similar noise floor to hits, but BENCHMARKS.md §4.4 hypothesizes a better signal-to-noise ratio since K-rate is more skill-driven — untested).

What is the model actually good and bad at? answered — reused existing, tested dashboard tooling

Raised in review: PA-grain noise makes it hard to reason about specific weaknesses like "the model underperforms once a batter has faced the same pitcher 3 times." shared/model_dashboard/ already has exactly the tool for this — slice generation, a log_loss-contribution ranking, and bootstrap CIs to separate real gaps from small-sample noise — built per CLAUDE.md's Model Layer section, never wired to this model's actual predictions until now. Slice-average log_loss (not resolution) is the right lens here: unlike resolution it isn't fooled by n=1 noise as long as a slice pools enough PAs, same principle as the matchup-extremity grid earlier — min_n raised to 500 from the dashboard's default of 50 for exactly that reason.

Open questions

#1 Naive's game-grain resolution (0.0182) is still unbeaten. Three separate attempts (ML models v1–v5, this shrinkage baseline, n_pa predictor v1) have all fallen short of it.
✓ Matchup-extremity slice check — done, see card above. Finding cuts both ways: even the most extreme matchup only spans 0.202–0.242 observed (not near-zero), and the shrinkage baseline currently ignores pitcher quality entirely (batter-only model) despite the real data showing a consistent, real pitcher effect within every batter tier.
✓ Adding pitcher signal (log5, v1 static) — flat (calibration_only). Resolution went down slightly (0.0159→0.0155). Diagnosed via Blake Snell's actual game log: the pitcher term is a static last-season snapshot, no in-season updating — unlike the batter term, which already blends last-season with in-season cumulative tracking.
✓ Blending the pitcher side (v2) — done, see card above. Verdict: real_improvement, both vs batter-only (resolution +0.0003, reliability better) and vs v1 static (resolution +0.0006). The diagnosis held up when tested: giving the pitcher side the same cascading in-season treatment the batter side already had fixed it. Beats batter-only on every metric in the table, not just the decision pair. Still below naive's resolution (0.0162 vs 0.0182) — real progress, not a full close.
#2 Why do v1–v5 (gradient-boosted/RF, dozens of features) underperform this formula's reliability? ROADMAP.md backlog item 2. Now sharper evidence either way: a maximally clean, incrementally-verified, hand-traceable approach — batter shrinkage → matchup grid → static pitcher term → blended pitcher term — got a real, measured win each time signal was added correctly. The ML models, with far more features thrown in at once, still haven't beaten this. Points toward "bundling + no per-addition verification" as the more likely explanation than "the right feature hasn't been tried."
#3 v4/v5 never logged game-grain reliability, so no full verdict is computable for them retroactively — only resolution/ROC-AUC/Brier were captured. Future experiments get this for free.
