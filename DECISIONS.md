## 2026-09-17 (4) — Event-driven trigger chain built: `daily_lineup_fetch → daily_feature_create → daily_feature_materialize`

Follow-up to the `event_timestamp` fix directly below, run through `/impl-planning` per this repo's TDD rule. Replaces the fixed-daily-cron idea discarded earlier this session (day/night games confirm lineups at very different real times, so no single schedule serves both well) with a real S3-event trigger: `daily_lineup_fetch`'s `write_lineup` already writes one file per confirmed game (`raw_data/games/lineups/{year}/{date}/{game_pk}.json`) — that write now triggers `daily_feature_create` directly, which on success invokes `daily_feature_materialize` asynchronously. No Step Functions — a two-hop chain doesn't need the state-machine infra `daily_pipeline` (`data_fetch → data_process`) uses for a more complex flow.

**Two real constraints found before writing any Terraform, not assumed:**
1. Confirmed via `grep` that the `mlbdk` bucket has no existing `aws_s3_bucket_notification` anywhere in `terraform/main.tf` — only one such resource can exist per bucket in Terraform (a second one silently replaces rather than merges with an existing config), so this needed checking first. It didn't exist, so adding one was safe.
2. `daily_lineup_fetch` also writes a states-tracking file (`raw_data/games/lineups/states/{year}/{date}.json`) to the *same* prefix on every 15-minute poll cycle, whether or not anything new confirmed that cycle — S3's notification filters only support prefix/suffix matching (no regex/exclude), so a filter alone can't tell a real per-game confirmation from this wrong-granularity states write. Fixed by having `daily_feature_create`'s own handler detect and skip it: `_date_from_event` checks whether the key's 4th path segment (0-indexed) is literally `"states"` rather than a year, and returns early with a clean 200 no-op rather than treating it as a real event.

**Code (`daily_feature_create/handler.py`):** `_date_from_event(event)` now understands two shapes — the existing direct-invoke `{"date": "..."}` (used for manual smoke tests, unchanged) and a real S3 event notification (`event["Records"][0]["s3"]["object"]["key"]`), extracting the date from the key when triggered that way. On success (`succeeded` non-empty), the handler calls `lambda_client.invoke(FunctionName="daily_feature_materialize", InvocationType="Event")` — async, fire-and-forget, logged but not allowed to mask the real transform results in the response body if the invoke itself fails. 6 new tests, TDD'd red-green (all failed first for the same right reason — `lambda_client` didn't exist yet).

**Terraform:** `aws_lambda_permission.allow_s3_invoke_feature_create` (scoped via `source_arn` to the `mlbdk` bucket ARN) + `aws_s3_bucket_notification.feature_create_on_lineup_write` (prefix `raw_data/games/lineups/`, suffix `.json`, target `feature_create`) + `aws_iam_role_policy.lambda_invoke_feature_materialize` (grants `lambda_role` `lambda:InvokeFunction` scoped to `feature_materialize`'s ARN). `terraform validate` passes; `terraform plan` shows a clean 3-to-add, 0-to-change, 0-to-destroy — no drift elsewhere. Full suite: 672 passed (+5 net new), same one pre-existing unrelated failure as every session since 2026-08-27.

**Not done, deliberately:** no `terraform apply`, no zip rebuild/redeploy of `daily_feature_create` (which now needs one — it bundles both this trigger-chain code and the not-yet-deployed `event_timestamp` fix from the entry below; both ship together in the next redeploy, per the user's explicit call to hold off until this chain was built).

## 2026-09-17 (3) — `event_timestamp` fixed to reflect real lineup-confirmation time, not the calendar date

Follow-up to the deploy in the entry directly below, prompted by planning the next step: wiring `daily_lineup_fetch → daily_feature_create → daily_feature_materialize` to run per-game as lineups confirm through the day (day and night games confirm at very different real times, so a single fixed daily schedule can't serve this well — see the discarded EventBridge-cron approach earlier this session). Walking through that design surfaced a real correctness bug that would have silently broken it: `batter_lineup.py`/`batter_pa_volume.py`'s Feast-facing `event_timestamp` was pinned to the calendar date (midnight), not the real confirmation moment. `materialize_incremental()` tracks a watermark and only pulls rows with `event_timestamp` after the last materialized point — so a second same-day materialize call (after a later game's lineup posts) would see the newly-recomputed offline file's rows still stamped with today's midnight, already behind the watermark advanced by the first call, and silently skip them. The whole point of running materialize per-game would have been defeated by this.

**Fix, run through `/impl-planning` per this repo's TDD rule:** `daily_lineup_fetch`'s `build_lineup_payload` already writes a real per-game `confirmed_at` UTC timestamp into each lineup JSON — this data already existed, just wasn't used. `batter_lineup.py`'s `OUTPUT_COLUMNS` gained a `game_date` column alongside `event_timestamp`, so the two concerns are no longer conflated in one field: `event_timestamp` is the real Feast-facing freshness signal (`confirmed_at` for incremental, unchanged game-date-based for backfill — box scores have no real "confirmation moment"), and `game_date` is the calendar date `batter_pa_volume.py`'s point-in-time-safe rolling-window logic needs (its phantom-row construction and the `rolled["game_date"] == today_ts` filter must stay date-only, not a precise timestamp, or they'd stop matching). `parse_lineup_payload` strips `confirmed_at`'s timezone to naive UTC (`tz_localize(None)`) so its dtype matches backfill's already-naive timestamps — a mixed tz-aware/naive column breaks once both sources land in the same Parquet file.

One existing test's premise had to change, not just its fixture: `test_backfill_and_incremental_agree_on_batting_order_value` previously asserted backfill and incremental `event_timestamp` were equal — that's no longer true by design (backfill's is the game date, incremental's is a real confirmation moment; they're now different concepts). Changed the assertion to compare `game_date` instead, which is the value that should still agree between the two independent sources describing the same real-world game. 4 new tests (both files), TDD'd red-green throughout — including `test_compute_batter_pa_volume_features_for_date_uses_real_confirmed_at_not_midnight`, the direct regression proof for the bug (asserts a 10pm confirmation produces a 10pm `event_timestamp`, not midnight). Full suite: 667 passed (+3 net new), same one pre-existing unrelated failure as every session since 2026-08-27.

**Scope note:** this fixes the transform layer only. `daily_feature_create`'s deployed zip still bundles the pre-fix `batter_lineup.py`/`batter_pa_volume.py` — needs a `make zip-feature-create` + redeploy before this fix is live, and the actual `daily_lineup_fetch → feature_create → materialize` trigger chain (S3 event notification, per the earlier discussion this session) is still not built. Both are separate, explicitly deferred follow-ups.

## 2026-09-17 (2) — `daily_feature_materialize` deployed and proven live: 4 real bugs found in the process, none of them feast's

Continuation of the same day's split (entry directly below). User pushed the built image to a real ECR repo and ran `terraform apply` for real, which surfaced a chain of genuine deployment bugs — every one a real gap, not a retry-and-it-works flake. Documenting all four since a future agent redeploying this Lambda (or any future container-image Lambda in this repo) will hit the same class of issues.

**Bug 1 — `dk-user`'s IAM policy never anticipated Terraform managing ECR at all.** Four missing actions surfaced one at a time, each only visible once the previous one was fixed: `ecr:ListTagsForResource` (Terraform's AWS provider always reads tags on every taggable resource to populate the computed `tags_all` attribute, even when no `tags` block is set — this is provider-wide behavior, not specific to this resource), `ecr:SetRepositoryPolicy` and `ecr:GetRepositoryPolicy` (needed once `aws_ecr_repository_policy` was added — see Bug 2), `ecr:DeleteRepositoryPolicy` (Terraform tries to destroy+recreate a resource it marked tainted from an earlier partial-failure apply — see the pattern below). After the third fix, decided to stop patching the custom policy incrementally and just attached the AWS-managed `AmazonEC2ContainerRegistryFullAccess` policy directly to `dk-user` — reasonable here since `dk-user` already carries broad functional access elsewhere (`AmazonECS_FullAccess`, full S3 bucket access) for a solo project, not a tightly least-privileged account. `terraform/dk-user-policy.json` (the hand-maintained reference doc, not itself Terraform-managed — see the 2026-09-16 entry's point 3 for why) was kept in sync with each incremental fix along the way.

**Recurring pattern worth naming: partial-apply taint requires a matching delete permission.** Twice during this deploy (`aws_ecr_repository.feature_materialize` initially, then `aws_ecr_repository_policy.feature_materialize`), a resource's *create* call succeeded but Terraform's immediate follow-up *read* call failed on a missing permission — and Terraform marks the resource `tainted` when that happens, meaning the *next* apply attempts destroy-then-recreate, which needs the *delete* permission too, compounding the missing-permission list. Both times the actual fix was `terraform untaint <resource>` once the read permission landed, since the resource was genuinely fine — no delete/recreate was ever actually needed. Worth checking `terraform state show <resource>` for `(tainted)` before assuming a new permission error means the resource itself is broken.

**Bug 2 — creating an ECR repo does not grant the Lambda *service* permission to pull from it.** First real `aws_lambda_function.feature_materialize` creation attempt failed with `AccessDeniedException: Lambda does not have permission to access the ECR image` — this is a completely separate axis from `dk-user`'s own IAM permissions (which only govern who can *push*/manage the repo). Fixed by adding `aws_ecr_repository_policy.feature_materialize`, a resource-based policy on the repo itself granting `lambda.amazonaws.com` (scoped via `aws:sourceArn` condition to this specific function's ARN) `ecr:BatchGetImage`/`ecr:GetDownloadUrlForLayer`. Built the function's ARN from known literals (region + hardcoded account id, matching how Lambda layer ARNs are already referenced elsewhere in this file) rather than `aws_lambda_function.feature_materialize.arn`, to avoid a dependency cycle — the Lambda needs this policy to exist before it can be created, so the policy resource has an explicit `depends_on` from the Lambda side instead.

**Bug 3 — image built on Apple Silicon defaulted to `arm64`; the Lambda function defaulted to `x86_64`.** First real invoke after the function was finally created returned `Runtime.InvalidEntrypoint: ProcessSpawnFailed` — a real architecture mismatch, not a code bug. `docker inspect`'s `.Architecture` confirmed `arm64` (Docker's native default on this Mac); Lambda functions default to `x86_64` unless `architectures` is explicitly set. Fixed by adding `architectures = ["arm64"]` to `aws_lambda_function.feature_materialize` to match the already-pushed image, rather than rebuilding for `x86_64` — also a modest cost win (arm64 Lambda pricing is ~20% cheaper per ms). This is specific to this one container-image Lambda; every other Lambda in this repo is zip-based and defaults to `x86_64` with no issue, since there's no local-build-architecture question for a zip.

**Bug 4 — `s3fs` was missing from the container image's `requirements.txt`.** First real invoke after fixing Bug 3 got past the entrypoint and actually ran `materialize_incremental()`, which failed for real: `ImportError: ... Install s3fs to access S3` — Feast's file-based offline store reads its `FileSource` Parquet via pandas, which delegates `s3://` paths to `s3fs`/`fsspec`, and `s3fs` was never in the image's dependency list (only `numpy`/`pandas`/`pyarrow`/`feast[aws]` were, per the 2026-09-17 (1) entry). The root `requirements.txt` already pins `s3fs==2026.7.0` for the same reason (local dev), but that exact version couldn't be reused here: `feast[aws]==0.62.0` caps `fsspec<=2024.9.0`, and `s3fs==2026.7.0` needs a much newer `fsspec` — a genuine, unresolvable-as-pinned version conflict specific to this image (the root project doesn't hit it because `awswrangler`, not `feast`, is what pulls `fsspec` there, with a looser range). Left `s3fs` unpinned in this Dockerfile's `requirements.txt` instead of copying the root pin; pip resolved `s3fs==2024.9.0` (paired with the same `fsspec==2024.9.0` feast already required), verified via a real container exec (`import s3fs; s3fs.S3FileSystem()`) before pushing again.

**Real end-to-end proof, once all four were fixed**: re-pushed the corrected image, ran `aws lambda update-function-code` (required — Terraform's `ignore_changes = [image_uri]` means a new push to `:latest` doesn't auto-propagate to an already-deployed function, same reasoning as the zip Lambdas' `ignore_changes = [filename, source_code_hash]`), waited for `LastUpdateStatus: Successful`, then invoked for real. CloudWatch logs confirm both `batter_pa_volume_fv` and `batter_lineup_fv` materialized from `2024-06-15` (the real prior watermark left by 2026-09-15's one-time historical `feast materialize` call — see that entry) to `2026-09-18`, ending in `materialization complete`. `aws dynamodb scan --select COUNT` on `mlb_predictions.batter_lineup_fv` confirms 600 items (up from the 399 recorded 2026-09-15, consistent with new games since then).

`daily_feature_materialize` is now a real, working, deployed Lambda — this is the first time any part of this repo's Feast-based FTI pipeline has run materialization from inside AWS rather than from a local machine. Still not scheduled (no EventBridge rule) — that remains the next, explicitly deferred step.

## 2026-09-17 (1) — Split `daily_feature_create` in two: `feast` doesn't fit a zip+layers Lambda

Follow-up to yesterday's step-3 fix, prompted by the user resolving an ambiguity that fix had deliberately left open: whether `daily_feature_create`'s Terraform ownership (flagged as unresolved 2026-09-16) was actually a real open question. It wasn't — Terraform already lives in this repo (`terraform/main.tf` manages every other Lambda), so the natural move is to add this Lambda there too, not leave it hand-deployed.

**Real blocker found while doing that**: `feast[aws]==0.62.0`'s actual runtime dependency closure is ~470MB (`pip install feast[aws]==0.62.0` into a clean target dir, measured directly — not a guess). Even after excluding what the `AWSSDKPandas-Python311` layer already covers (`pandas`/`pyarrow`/`numpy`/`botocore`, ~254MB of that total), the remaining feast-specific closure is ~216MB — largely from things a batch materialization job never touches at runtime: `dask` (15MB, an optional feast ingestion backend), `SQLAlchemy[mypy]` (a real feast packaging quirk — pulls a dev-time type-checker plugin into runtime deps), and feast's own optional registry-server/UI stack (`fastapi`/`uvicorn`/`starlette`). Stacked on the pandas layer's own footprint, this doesn't fit Lambda's 250MB combined zip+layers cap.

**Decision, after walking through it with the user**: this is a known, common issue for any moderately heavy Python data/ML dependency in Lambda's zip-based model — not specific to feast or to this repo. The standard fix AWS built for exactly this case is a container-image Lambda (`package_type = "Image"`, up to 10GB, no layers). The alternative (hand-trimming feast's install to a minimal runtime-only subset) was rejected as fragile — a feast version bump could silently re-break it with no test able to catch the gap until a real invoke fails.

**This surfaced a cleaner split than "make the whole Lambda a container image," though**: Feast's own FTI (Feature/Training/Inference) architecture already separates feature computation (writes to the offline store, no `feast` SDK needed) from materialization (offline → online sync, the only place `feast` has to load) — orgs running Feast at real scale keep these as decoupled jobs precisely so the heavy SDK isn't loaded by the lightweight compute step. Applied here:

- **`daily_feature_create`** (existing Lambda, fixed 2026-09-16) — `feast` import removed entirely (`from feast import FeatureStore` and the `materialize_incremental()` call/response-shape deleted from `lambda_handler`). Still just computes `batter_lineup`/`batter_pa_volume` and writes Parquet to S3, now a normal zip+layers Lambda with zero size risk. 9 tests updated (TDD red-green: added `test_handler_module_never_imports_feast`, confirmed RED via `hasattr(feature_create_handler, 'FeatureStore')` before the removal; deleted the now-meaningless `test_materialization_error_stored_under_correct_key`, replaced with `test_handler_returns_207_when_a_transform_fails` covering the same partial-failure path minus materialization).
- **`daily_feature_materialize`** (new Lambda, `src/lambdas/daily_feature_materialize/handler.py`) — the only place `feast` gets imported; calls `FeatureStore(repo_path=...).materialize_incremental(end_date=now)`, returns 200/500. 3 tests, TDD red-green (mocks `feast` at `sys.modules` level, same pattern as every other handler test in this repo).

**Container image built and verified for real, not assumed from `docker build` exiting 0** — this took two real, non-obvious fixes along the way:
1. First build attempt (`public.ecr.aws/lambda/python:3.11` base image) failed installing `numpy`: no prebuilt wheel found, fell back to a from-source build, which then failed with no C compiler present (`cc`/`gcc`/`clang` all missing). Root cause, confirmed by inspecting the base image directly (`cat /etc/os-release`): AWS's `python:3.11` Lambda base image runs **Amazon Linux 2** (glibc ~2.26) — genuinely too old for numpy/pyarrow's current `manylinux_2_28` wheels (confirmed via PyPI's own file listing for `numpy==2.3.1`, which ships only `manylinux_2_28` for cp311/aarch64, no older-glibc wheel at all). Upgrading pip first didn't help — pip's tag rejection was *correct*, not a detection bug.
2. Fix: switched the base image to `public.ecr.aws/lambda/python:3.12`, confirmed via the same `/etc/os-release` check to run **Amazon Linux 2023** (glibc 2.34) — real prebuilt wheels install cleanly. A container-image Lambda's Python version is independent of this repo's other Lambdas' `python3.11` runtime, so this is a contained, low-risk choice, not a repo-wide version bump.
3. Real verification, not just a successful `docker build`: ran the built image locally via `docker run -p 9123:8080 ...` (the base image bundles the Lambda Runtime Interface Emulator) and POSTed a real invoke to `http://localhost:9123/2015-03-31/functions/function/invocations`. Result: `feast` imported successfully and `materialize_incremental()` ran all the way to a genuine `NoCredentialsError` from its DynamoDB call — the expected, correct failure mode for a sandboxed environment with no real AWS credentials, and proof the packaging itself has no gap. Final image: 1.03GB uncompressed, comfortably under Lambda's 10GB image cap.

**Terraform written for both Lambdas** (`terraform/main.tf`): `aws_lambda_function.feature_create` (zip+layers, `AWSSDKPandas-Python311` layer only — this layer bundles `awswrangler` together with `pandas`/`numpy`/`pyarrow`, which closes the runtime-dependency gap flagged in yesterday's entry, since `data_readers.py` needs `awswrangler`); `aws_ecr_repository.feature_materialize` + `aws_lambda_function.feature_materialize` (`package_type = "Image"`, `image_uri` pointed at that repo's `:latest` tag, `ignore_changes = [image_uri]` so future image pushes don't fight Terraform the way the zip-based Lambdas already `ignore_changes` on `filename`/`source_code_hash`); `aws_iam_role_policy.lambda_dynamodb_feast` granting `GetItem`/`PutItem`/`BatchWriteItem`/`DescribeTable` scoped to `arn:aws:dynamodb:us-east-2:*:table/mlb_predictions.*` (the existing `lambda_s3_access` policy already covers the S3 half — registry + offline store). `terraform validate` passed; **no `terraform apply`, no ECR push, no EventBridge scheduling** — all explicitly out of scope for this pass, same as yesterday's zip-bundling step. The ECR image must be pushed before a first real `apply` can succeed (Terraform can't create an `aws_lambda_function` referencing an image that doesn't exist yet in the repo) — flagged, not done.

Full test suite: 664 passed (3 net new for `daily_feature_materialize`, one net-new/one-net-removed for `daily_feature_create`'s materialization-removal), same one pre-existing unrelated failure as every session since 2026-08-27.

## 2026-09-15 (8) — FTI step 2 complete: first real `feast apply` + `materialize` + `get_online_features()` this repo has ever run

Continuation of the entry directly below, which left off with code/config ready but nothing actually executed against real infra. Ran it for real; found three more real bugs along the way, none of them Feast's logic being wrong — all pre-existing gaps in this repo's own setup that had simply never been exercised before, because `feast apply` had literally never run before today.

**Bug 1 — `.feastignore` was a complete no-op, for two independent reasons.** The tracked file was named `.feastignore ` (trailing space — Feast's CLI looks for the exact literal name `.feastignore` and silently never found it), and its one line of content was `.transforms/` (stray leading dot — even if the filename had been right, this pattern would never have matched the real `transforms/` directory). Net effect: `feast apply`'s repo scanner walked into `src/features/transforms/` and tried to import `batter_lineup.py`, which failed (`ModuleNotFoundError: No module named 'data_readers'`) because that file's sibling-style import only resolves when `transforms/` itself is on `sys.path` — true for Lambda bundling and for tests via `conftest.py`, not true for Feast's own import mechanism. Fixed by renaming the file and rewriting its content to `transforms/\n`.

**Bug 2 — a real, incompatible `pyarrow` version range between `feast` and `awswrangler`.** `feast[aws]==0.62.0` requires `pyarrow>=21.0.0`; `awswrangler==3.12.1` states `pyarrow<21.0.0`. No single version satisfies both — genuinely incompatible ranges, not a resolvable pin. Tested pyarrow 25.0.1 (feast's floor) against `awswrangler`'s actual read path (not just its stated constraint) and the full test suite: both green. Took feast's floor rather than hunting for an old feast release matching awswrangler's ceiling — awswrangler's pin is almost certainly more conservative than what it actually needs. `requirements.txt` updated (`pyarrow==25.0.1`, `feast[aws]==0.62.0`, `aiobotocore==2.23.1`, `s3fs==2026.7.0` — `feast` itself was never in `requirements.txt` at all before this, despite being used in this repo for months; also restored `boto3==1.38.46` after feast's resolver silently downgraded it to `1.38.27`, since that specific downgrade wasn't required by anything).

**Bug 3 (this one mine, not pre-existing) — used `materialize-incremental` for a task it isn't designed for.** First attempt (`feast materialize-incremental 2024-06-15T00:00:00`) reported success with no error but wrote zero rows to DynamoDB — caught by actually scanning the table rather than trusting the CLI's clean exit. Root cause, confirmed via `FeatureStore.get_feature_view(...).materialization_intervals`: `feast apply` itself sets an initial high-water-mark near real wall-clock apply time, so `materialize-incremental`'s "from last watermark to end_date" computed an inverted, empty range when `end_date` (a 2024 date) was earlier than that watermark (~2026-09-16). `materialize-incremental` is the right tool for *ongoing* production use (advancing forward from wherever a real daily job last left off) — for a first-time historical load, `feast materialize <start_ts> <end_ts>` (explicit range, no watermark involved) is the correct command, and is what step 3's future daily job would call incrementally once it's actually running on a schedule.

**Real end-to-end proof, once all three were fixed:**
